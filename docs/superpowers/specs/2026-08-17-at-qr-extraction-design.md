# AT QR Code Extraction — Design

**Date:** 2026-08-17
**Status:** Approved
**Extends:** [2026-08-16-image-bill-ingestion-design.md](2026-08-16-image-bill-ingestion-design.md)

## Goal

Detect and decode the Portuguese tax-authority (AT) QR code printed on supplier invoices,
and use its fields in preference to what the vision model reads off the page.

Portuguese invoicing software must print a QR code whose contents are fixed by Portaria
195/2020. It carries, among other fields, the issuer's NIF and the buyer's NIF **in separate
labelled fields**. That is a structural solution to the defect the previous cycle spent four
tasks on: the vision model returned the buyer's NIF as `supplier_tax_id` on one invoice and a
misread digit on another, because on a photographed page the two numbers are distinguishable
only by layout and label, and the labels are not reliable.

A decoded QR is machine-generated by certified software. It does not misread digits.

## Field reference (Portaria 195/2020)

The payload is `KEY:VALUE` pairs joined by `*`. Fields this design consumes:

| Field | Meaning | Maps to |
|---|---|---|
| `A` | Issuer's NIF | `supplier_tax_id` |
| `B` | Buyer's NIF | `buyer_tax_id` |
| `D` | Document type (`FT`, `FS`, `FR`, `NC`, `ND`, …) | warning only |
| `E` | Document status (`N` normal, `A` cancelled, …) | warning only |
| `F` | Document date, `YYYYMMDD` | `issue_date` |
| `G` | Unique document identifier | `number` |
| `H` | ATCUD | not consumed |
| `I2/I3/I5/I7` | Taxable bases (mainland: exempt, reduced, intermediate, normal) | `net_total` |
| `I4/I6/I8` | VAT amounts (reduced, intermediate, normal) | not consumed individually |
| `J*`, `K*` | Açores and Madeira equivalents of the `I` fields | `net_total` |
| `L` | Non-subject amount | `net_total` |
| `N` | Total tax | `vat_total` |
| `O` | Document total with tax | `gross_total` |

Unknown or unlisted fields are ignored, not an error — the format allows fields this design
does not consume, and future ones must not break decoding.

## Architecture

```
original upload bytes
      │
      ├──► qr.decode(data) ──► payload string | None
      │                              │
      │                              ▼
      │                     at_qr.parse(payload) ──► AtQr | None
      │                                                  │
      └──► prepare() ──► parse_image() ──► Bill ──► merge ──► Bill (+warnings)
                                                              │
                                                              ▼
                                                    Matcher ──► BillProposal
```

### `logic/bills/extract/qr.py` (new)

`decode(data: bytes) -> str | None` — locate and decode the first AT-shaped QR payload.

Runs on the **original** bytes with only EXIF rotation applied. It must not receive the
output of `prepare()`: that downscales to a 1568px long edge, and at the observed sizes the
QR is already near the decodable limit. Losing pixels there loses the feature.

Returns `None` when no QR is found or none decodes. Never raises for an undecodable image —
absence of a QR is the normal case, not a failure.

### `logic/bills/extract/at_qr.py` (new)

`parse(payload: str) -> AtQr | None` — split on `*`, then on the first `:` of each pair.
Returns `None` unless the result carries at least `A` and `O`, which is what distinguishes an
AT invoice code from any other QR that happens to be on the page.

This module touches no image library and imports nothing outside the standard library and
Pydantic. All field semantics are therefore testable without the decoder installed.

### Merge — `logic/bills/extract/at_qr.py`

The merge is a pure function in the same module as the parser, not a method on
`BillService`: `merge(bill: Bill, qr: AtQr) -> tuple[Bill, list[str]]`, returning the amended
bill and the warnings raised. `BillService._extract` calls `decode` → `parse` → `merge` and
passes the warnings up to `upload`, where they join `arithmetic_warnings(bill)` in the
existing `warnings` list.

Keeping it a pure function means the whole merge policy is testable without an image, a
decoder, a database reader, or an Anthropic client.

When a QR parses, its values overwrite the vision-extracted `Bill`:

- `supplier_tax_id` ← `A`, `buyer_tax_id` ← `B`, `number` ← `G`
- `issue_date` ← `F` (parsed from `YYYYMMDD`)
- `vat_total` ← `N`, `gross_total` ← `O`
- `net_total` ← the sum of the taxable bases (`I2/I3/I5/I7`, the `J` and `K` equivalents, and
  `L`) when any are present; otherwise `O − N`

Line items always come from vision. The QR contains no line detail, so this is not a choice.

Every field where the QR and the vision output disagree produces a warning naming both
values, so the operator sees what the model got wrong rather than having it silently
corrected. Warnings join the existing `BillProposal.warnings` list.

Two further warnings come free from the format:

- `E` other than `N` means the document is **cancelled or otherwise not normal**. Ingesting a
  cancelled invoice is a real accounting error, so this warns loudly.
- `D` outside the invoice types (`FT`, `FS`, `FR`) means the document is a credit note or
  something else that this pipeline does not model as a purchase invoice.

The `supplier_tax_id` NIF check-digit guard added in the previous cycle still applies after
the merge. A QR-sourced NIF will pass it — that is the point — but the guard stays in place
rather than being bypassed on the assumption that QR data is always well-formed.

## Decoder choice — decided by evidence

No QR library is currently installed, so this feature costs a new dependency. Two candidates:

- **`opencv-python-headless`** — a pure pip wheel needing no system package. Given how much
  trouble Tesseract and Poppler have caused in deployment, that is worth real weight.
- **`pyzbar`** — a binding to zbar, generally stronger on photographed codes, but requiring
  `libzbar0` from apt on Linux.

**The first task is a throwaway spike** that tries both against all six example invoices, at
full resolution and with the QR region upscaled, and reports what actually decodes. The
dependency is chosen from that result. If neither decodes anything, the feature degrades to
vision-only and the cost of finding out was one task.

This is not defensive hedging. The examples are 1080×1920, and the QR on `scanner_forumsi_1`
occupies roughly 120×120 px. An AT payload of ~150–200 characters implies roughly 49–61
modules per side — about two pixels per module before JPEG artefacts and camera blur. Whether
that decodes is an empirical question, and designing around a guess would be wrong.

## Error handling

| Condition | Behavior |
|---|---|
| No QR in the image | `decode` returns `None`; vision output used unchanged |
| QR present but undecodable | `decode` returns `None`; vision output used unchanged |
| QR decodes but is not an AT code | `parse` returns `None`; vision output used unchanged |
| QR field missing or malformed | That field is not overwritten; others still apply |
| Decoder library not installed | `decode` returns `None`; the pipeline still works |
| `E` ≠ `N`, or `D` not an invoice type | Merge proceeds, warning added |

The controlling principle: **the QR can only ever improve the result.** No QR condition may
make ingestion fail that would otherwise have succeeded. This mirrors the treatment already
given to `bills_examples/scanner_forumsi_4.jpeg`, a Spanish supplier's invoice with no QR at
all, which must continue to work exactly as it does today.

## Testing

**Pure parsing tests** (`tests/bills/test_at_qr.py`) — no image, no decoder dependency:
payloads built from the real invoices' printed data; the `A`/`B` distinction; `F` date
parsing; net-total derivation both from base fields and from the `O − N` fallback; unknown
fields ignored; non-AT payloads rejected; malformed input returning `None` rather than raising.

**Merge tests** (`tests/bills/test_service.py`) — QR values overwrite vision's; disagreements
warn; a missing QR leaves the bill untouched; cancelled status warns; line items survive the
merge unchanged.

**Decode tests** (`tests/bills/test_qr.py`) — run against the real files in `bills_examples/`,
which is untracked in git. These **skip** when the directory or the decoder is absent, rather
than failing. Five of the six invoices carry a QR; `scanner_forumsi_4` does not and must
return `None`.

**Live verification** — re-run the six examples end to end and produce a before/after table
for `supplier_tax_id`, `number`, `issue_date` and the totals. The previous cycle's measured
baseline is `supplier_tax_id` correct on 5 of 6, with `scanner_forumsi_1` returning
`502267583` where the footer reads `502667583`. If the QR decodes on that invoice, this cycle
should take it to 6 of 6.

## Out of scope

- Validating the ATCUD (`H`) against AT's registry.
- Checking the buyer NIF (`B`) against the operating company's own NIF to detect misfiled
  bills — worth doing later, but the company NIF is not configured anywhere today.
- Reading QR codes from PDFs.
- Barcode formats other than QR.
- Any change to matching, staging, committing, or the write path.
